# Spike S3: pagination in ProseMirror

Task V1-S3 (HLD §20 S3). The prototype is in `spikes/S3/`. The raw results are in `spikes/S3/results/*.json`.

## Verdict

The LLD P3 §10–§11 design works in a real browser. On a 201-page document, the Chromium work for a typing edit is about 2–3 ms (median), and for an insert that moves blocks across every later page it is 4.6 ms median and 7.6 ms p95. That leaves a lot of room in a 16.7 ms frame. The layout model, the spacer widgets, the resume-from-first-change pass, the `WeakMap` height cache and the lazy header/footer copies all work as designed.

Five details in the LLD need correcting. Without them, page frames and content come apart:

- C1: how block heights are read
- C2: the units the geometry is snapped to
- C3: blocks taller than one page (PO-23)
- C4: what state the measure pass resumes from
- C5: the spacer key and how copies are refreshed

They are listed under "Corrections" below. They change the LLD text, so they need the project owner's approval (AGENTS.md §7).

**Fixture.** `buildDoc` in `src/main.js` builds a deterministic document:

- **Page:** A4 portrait with 72 pt (2.54 cm) margins (PO-26).
- **Header:** "page `{number}` of `{count}`", using `page_field` nodes (PO-21).
- **Footer:** "page `{number}`".
- **Body blocks:**
  - paragraphs of 20–120 words
  - an `h2` every 12th block
  - an image-like fixed-height box every 50th block
  - a `page_break` every 150th block
  - two blocks taller than a page (PO-23): a 1,200 pt box at block 30 and a 2,500-word paragraph at block 60
- **Text style:** Arial 16 px with line-height 1.15, so line heights are fractional.

| Blocks | Pages |
|---|---|
| 1,420 | 201 (the main case) |
| 2,130 | 302 (the LLD E2E size) |
| 3,550 | 500 |

**How we measured.** Measurements run inside the page through `window.S3`, with `performance.now()`. Each scenario is a sequence of samples on one document, so the edits add up as the run goes on. The sample counts (n) are in the tables. The phases are:

| Phase | What it covers |
|---|---|
| `dispatch` | `view.dispatch(tr)`: ProseMirror's transaction plus its DOM update |
| `pass` | the measure pass in the next `requestAnimationFrame`: its DOM reads, which force a layout, the arithmetic, the decoration build and the single meta `dispatch` |
| `layoutAfter` | a forced layout read right after the pass, which is the layout the frame would otherwise do |
| `work` | `dispatch` + `pass` + `layoutAfter` = main-thread cost per edit, excluding paint |

For the keyboard rows we also took two more measurements:

- Real key presses (Playwright `keyboard.press`), timed from the `keydown` event to the end of the pass.
- The Chromium Event Timing API's `keydown` duration (input to next paint). The browser rounds this to 8 ms and reports only values of 16 ms or more.

The pass runs in `requestAnimationFrame`, so the text change and the new page breaks are painted in the same frame.

**Correctness check.** `S3.verify()` is asserted in the test:

- Every block that fits on a page must lie inside its page frame's body box (tolerance 0.5 px).
- The editor's bottom edge must match the bottom of the last frame.

**Reproduce:**

```

npm ci
node build.mjs
S3_BLOCKS=1420 node ../../node_modules/@playwright/test/cli.js test --config playwright.config.mjs
```

## Chosen approach

This follows LLD P3 §10–§11, with corrections C1–C5. The code is in `spikes/S3/src/`.

**Layout model** (as in the LLD):
- The editor DOM is exactly one page wide, with padding equal to the margins.
- Body children get `margin: 0`, plus `box-sizing: border-box` (see C1).
- `.odx-page-frames` is a background layer of absolutely positioned page rectangles.
- The real `header` node view is page 1's top-margin box. Its height comes from a node decoration (`bodyTop`) and its content is aligned to the bottom.
- The real `footer` is the last child. A `tail` widget pushes it into the last page's bottom-margin box.

**Measure pass** (`pagination.js`):
- It runs in `requestAnimationFrame` after view updates, and is skipped and rescheduled while `view.composing`.
- It finds the first changed top-level body block by node identity, uses a `WeakMap<Node, height>` cache, and does DOM reads only.
- It ends with at most one `setMeta` dispatch, and none when nothing changed.
- There is a loop guard of 2 passes per frame. Fonts `loadingdone` and header/footer `ResizeObserver` callbacks invalidate the pass from block 0.

**Spacer widget:**
- `Decoration.widget(beforePos, …, { side: -1, key, ignoreSelection: true })`.
- It is a non-editable flex column holding: a filler, the footer-copy slot, the gap, and the header-copy slot.

**Copies** (`regions.js`):
- Built with `DOMSerializer.nodesFromSchema` and `marksFromSchema`, with `page_field` overridden. Copies use `textContent` only, never `innerHTML`.
- The serialized fragment is cached per node identity and cloned per page.
- The copy root has `contenteditable="false"`, `aria-hidden="true"` and `inert`.
- Copies are filled lazily: an `IntersectionObserver` with `rootMargin: '200% 0px'` (±2 viewports) watches the spacers.
- Measured: at most 7 header copies were in the DOM at once, and 158–160 copies were built over a whole run that scrolled to page 1 and to the last page.
- The real header shows page 1; the real footer shows the page count.

**Confirmed from the LLD, as measured:**
- One-page-wide DOM.
- Exact height sums with margin 0.
- Block-level pagination where the whole block moves to the next page.
- Forced breaks after `page_break`.
- The resume-from-first-change pass, where a typing edit re-measures exactly 1 block.
- The `WeakMap` cache: a header-height change re-lays out every page with 0 DOM height reads.
- A single meta dispatch with no layout thrash.
- Widget keys reuse spacer DOM.
- Lazy copies via `IntersectionObserver`.
- View-only documents paginate in the same way, since there is no editing-specific code in the pass.

## Corrections to LLD P3 §10–§11 (proposed; they need approval)

- **C1: measure with snapped computed style, not `offsetHeight`.**
  - `offsetHeight` is rounded to an integer, and the rounding adds up. Measured: content was 119 px off the frames by page 201, and 285 px off at 500 pages.
  - `getBoundingClientRect()` is float geometry relative to the viewport. It loses precision far from the viewport: the maximum block error was 0.19 px at 500 pages.
  - It also triggered full re-layouts. The header height read through it changed after scrolling to the last page, and that invalidated the whole pass.
  - The fix is `Math.round(parseFloat(getComputedStyle(el).height) * 64) / 64`, on blocks with `box-sizing: border-box`, and the same for `measuredHeight()`. Chromium lays out in 1/64 px units, and serializing the value adds at most 0.005 px of error, so snapping restores the exact value.
  - The LLD's jsdom unit test stubs `offsetHeight`. It would need to stub this read instead.
- **C2: snap `pageGeometry` values to 1/64 px.**
  - A4 is 1122.52 px tall. Without snapping, each spacer's height is rounded by the browser and the error adds up down the page stack.
  - Measured at 201 pages with unsnapped geometry: the first block more than 0.5 px out of its box was on page 119, and the editor ended 1 px short of the last frame. With the geometry snapped but the header height unsnapped, it ended 1.64 px short.
- **C3: PO-23 overflow.**
  - The LLD's spacer formula `(cap − y) + …` goes negative after a block taller than `cap`.
  - The frame positions `top = p · (heightPx + gapPx)` are then wrong for every later page.
  - The prototype records `overflow = max(0, y − cap)` for each page. It stretches that page's frame by the overflow, adds the overflow to the spacer, and positions frames cumulatively (`pageExtra` in `PaginationState`).
  - The resulting look is a question for the owner (Q1).
- **C4: resume state.**
  - The pseudocode resumes from `yBefore[s]` and `pageOf[s]`. Those values are stored after block `s`'s own break decision, so resuming from them loses whether block `s` itself starts a new page.
  - Instead, store the state before the decision (`yPre[i]`, `pagePre[i]`, and `posOf[i]`), and keep only the breaks with `index < s`. Breaks need an `index` field.
- **C5: spacer key and copies.**
  - The key `'pb' + page + ':' + spacerPx` is not enough:
    - The spacer's slot heights depend on `bodyTop` and `footBox`, so both must be in the key.
    - The `page_field` count in copies changes when the page count changes, but the key does not.
  - The prototype handles this with a copy generation, made of the header node id, the footer node id and `pageCount`. When the generation changes, it re-fills visible copies and clears the hidden ones (`refreshCopies`).
  - It also updates the real header's and footer's fields in place.

**Other observations:**
- An insert on page 1 changes every later spacer's height, so every spacer widget's DOM is rebuilt. This is the main cost at 500 pages (p95 27 ms). It stays within budget at 200 pages (p95 7.6 ms) and 300 pages (p95 17.5 ms, slightly over one 16.7 ms frame).
- A possible improvement, not needed for V1 sizes: key spacers by page only, and update their height in place.

## Open questions

- **Q1 (product, PO-23):** How should a page with a block taller than one page look?
  - In the prototype, that page's frame is stretched to fit the block, and its footer copy is at the bottom of the stretched frame.
  - The alternative: keep A4-sized frames and let the block overflow across the gap. The footer and header copies would then need to be positioned absolutely from the frames layer, not inside the spacer.
- **Q2 (LLD):** The LLD's E2E test "a 300-page document stays under the S3 spike's frame-time budget" needs a number.
  - Measured at 302 pages: typing work p95 is 4.1–5.8 ms, and an insert that moves blocks has p95 17.5 ms.
  - A possible budget is "typing `work` p95 ≤ 8 ms at 300 pages on CI hardware". CI hardware will be slower than this machine. The owner should set the number.
- **Q3 (LLD):** Do C1–C5 go into LLD P3 §10–§11 (and the matching unit-test stubs)?
- **Q4 (LLD gap):** What happens when a block's height changes but its node does not?
  - Images load asynchronously and get a blob `src` from `AssetCache`. They change height without a node change, so the `WeakMap` cache stays stale.
  - The LLD has a `ResizeObserver` only on the header and footer. Options are a `ResizeObserver` on images or blocks, or `load` events on images. The spike used fixed-height boxes and did not test real images.
- **Q5 (not covered):** The spike did not exercise:
  - tables (prosemirror-tables) and lists
  - IME composition: the `view.composing` path is implemented but untested
  - web fonts: the `loadingdone` invalidation is implemented but untested, since the spike uses Arial
  - Firefox and WebKit
  - headed Chrome with GPU paint
  - low-end hardware

  All the numbers above come from one fast desktop CPU in headless Chromium.
