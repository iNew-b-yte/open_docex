## 4. Method

- **Import:** fixture (`.docx`/`.odt`) → LibreOffice → `.fodt`, then checked.
- **Export:** `features.fodt` (the shape our writer will produce) → LibreOffice → `.docx`/`.odt`. The result is converted back to `.fodt` and checked. LibreOffice's own reader is therefore the judge of export.
- **Round trip:** fixture → `.fodt` → same format → `.fodt`, checked after cycle 1 and cycle 2. This round trip goes through LibreOffice only; the FodtMapper does not exist yet.
- **Checks:** `lib/inspect.mjs` (a spike-only flat ODF reader with style-chain resolution) and `lib/checks.mjs`. There are 62 checks with expected values; lengths have a 0.3 mm tolerance. On the source `features.fodt`, all 62 pass, which validates the checker itself.

## 6. Findings on the failing checks and other mapper-relevant behaviour

### 6.1 Page margins of a Word file with header/footer (F01)

`features-word.docx` has `pgMar top=850 bottom=1134 header=425 footer=425` (body 15/20 mm, header/footer distance 7.5 mm). LibreOffice imports this as:
- `fo:margin-top=0.75cm`, with the header `fo:min-height=0.75cm` and `fo:margin-bottom=0.649cm`
- `fo:margin-bottom=0.75cm`, with the footer `min-height=1.251cm`

So the ODF page margin is the **header distance**. The body edge is margin plus header height.

The reverse is true too. LibreOffice exports our `fo:margin-top=15mm` (with a header) as `w:header=850 w:top=1216`, which moves the Word body edge down by the header height (21.45 mm).

The LLD §14.5 row maps `fo:margin-*` straight to `PageSettings.margins`. Word-origin files with a header or footer would therefore load with different margins. LibreOffice-origin files pass because LibreOffice writes and reads its own convention. **Question Q1.**

### 6.2 Image title/description through LibreOffice's `.docx` writer (F16)

- Import keeps `wp:docPr title` → `svg:title` and `descr` → `svg:desc`.
- Export of our writer-shaped `features.fodt` keeps both: `title="ALT-PNG" descr="ALT-PNG desc"`.
- But when the input to the `.docx` writer is a `.fodt` that LibreOffice itself produced on import, the written `.docx` has `descr="ALT-PNG&#10;ALT-PNG desc"` and no `title`. The re-import then has no `svg:title`.

The cause was not isolated. It does not affect our export path, which always writes our own FODT. It does show that alt text placement differs between the two attributes. **Question Q2.**

### 6.3 Other observations for the FodtMapper (no failure)

- **Fonts.** The font is given either as `style:font-name` (pointing to `font-face-decls`) or as a direct `fo:font-family` (LibreOffice writes this on `.docx` import). Whichever a style layer sets overrides the other from the lower layers. The style resolution in §14.5 must handle both.
- **Lists from `.docx`.** These come as `text:list text:style-name="WWNum1"`, with the paragraphs' automatic style also carrying `style:list-style-name` and the parent `List_20_Paragraph`. Nested lists have no style name of their own and inherit it.
- **Page breaks.** A `.docx` `w:br w:type="page"` at the end of a paragraph is imported as `fo:break-before="page"` on the next paragraph. Both §14.5 page-break rows give the same model.
- **Base64.** `office:binary-data` written by LibreOffice is line-wrapped with whitespace inside. The incremental base64 decoder in §14.4 must skip whitespace.
- **Pretty-printing.** LibreOffice pretty-prints `.fodt`, putting whitespace-only text nodes between block elements and inside `draw:frame`/`draw:image`. These must not become text.
- **Flat XML size.** Measured flat XML sizes:
  - The 13 KB `features.docx` imports as an 82 KB `.fodt` (6.3×).
  - A generated 100× repeat of the body (35 KB `.docx`, 38 KB `.odt`, with the same images reused) imports as a 1.5 MB `.fodt` (about 40×): images that are stored once in the zip are base64-embedded at every use.
  - This only matters near the limit, since `maxFlatXmlBytes = 4 × maxFileBytes` is an absolute cap. **Q7.**
- **Field values.** LibreOffice writes the computed page number and page count as the text inside `text:page-number` and `text:page-count`, for example `3`. The mapper must ignore that text.
- **Link styles.** Links imported from `.docx` carry `text:style-name="ListLabel_20_1"` (a LibreOffice artefact). Style resolution leaves the run otherwise unchanged.

## 7. Timings, concurrency and process handling (Windows)

| Case (features fixture unless noted) | Runs | min / median / max (ms) |
|---|---|---|
| Cold start: new seeded profile, first conversion (docx→fodt) | 3 | 5271 / 5317 / 5373 |
| docx → fodt (import), warm profile | 5 | 2147 / 2163 / 2180 |
| odt → fodt (import) | 5 | 1723 / 1763 / 1835 |
| fodt → docx (export) | 5 | 1730 / 1763 / 1820 |
| fodt → odt (export) | 5 | 1787 / 1792 / 1842 |
| big (body ×100, 1.1 MB fodt) fodt → docx | 5 | 2461 / 2477 / 2534 |
| big fodt → odt | 5 | 2722 / 2809 / 2818 |
| big docx → fodt | 5 | 3567 / 3603 / 3735 |
| big odt → fodt | 5 | 2821 / 2826 / 2941 |
| image file → png (Draw), warm | 4 formats × several runs | about 1450–1700 per image |

Each `--convert-to` call starts a new LibreOffice process, so about 1.7 s of every warm conversion is process start-up. Content size adds comparatively little.

**Concurrency** (docx → fodt, `Promise.all`):

| Case | Jobs OK | Wall time (ms) | Per job (ms) |
|---|---|---|---|
| own profile slot each (warm) ×2 | 2/2 | 2425 | about 2410 |
| own profile slot each (warm) ×4 | 4/4 | 2671 | about 2630–2670 |
| own profile slot each (warm) ×8 | 8/8 | 3565 | about 3410–3560 |
| own fresh (cold) profile each ×4 | 4/4 | 7539 | about 7470–7520 |
| **one shared profile ×4** | **2/4** | 4728 | 2 jobs failed: exit code 1, **no output file, empty stdout/stderr** |

This confirms the LLD §14.3 design: one profile per concurrent conversion. A shared profile fails silently, apart from the exit code. No `soffice.bin` processes were left over after any concurrency batch (counted with `tasklist` after each batch).

**Blocking.** `soffice.exe` blocks until the conversion has finished. In more than 100 conversions, the output file always existed and was complete when the process exited; this confirms the note in LLD §14.2. The exit code was 0 on every success. `stdout` carries the line `convert … using filter : <name>` even with `soffice.exe` (not only `soffice.com`).

**Timeout and kill.** The big fodt → docx conversion was given a 1500 ms timeout:
- `taskkill /T /F` ended the whole tree after 1632 ms.
- The `soffice.bin` count was 0 before and 0 after.
- The re-created slot then converted successfully.

## 11. Blockers and questions for the project owner

None of these blocks V1 text import or export for the features in §5. Q1 and Q3 need a decision (and an LLD update) before the FodtMapper and image-conversion tasks.

- **Q1 (CL-9, LLD §14.5):** which convention does `PageSettings.margins` use?
  - The ODF convention: page edge to header, with the header inside the margin.
  - The Word convention: page edge to body.
  - Observed: a Word file with body margins 15/20 mm and a 7.5 mm header distance loads as 7.5/7.5 mm, plus header and footer heights. Our 15 mm ODF margin exports to Word as a 21.45 mm body margin.
  - Should the mapper derive body margins from margin plus header/footer height, or keep the ODF values?
- **Q2 (PO-24, §14.5 image row):** which attribute is the model's `alt`: `svg:title`, `svg:desc`, or both joined? In Word, "Alt Text" is `descr`, which maps to `svg:desc`. And what should export write?
- **Q3 (PO-22):** plain `--convert-to png` renders EMF, WMF and TIFF on a full A4 page, which is unusable. Observed working routes:
  - (c) a generated SVG wrapper plus `PixelWidth`/`PixelHeight`: exact size, about 1.5 s per image
  - (b) LibreOffice's built-in PNG fallback: EMF and WMF only, about 71 dpi
  - SVG converts directly.
  - Which route should we use, and at what resolution (dpi or pixel cap)? Should images be converted in one LibreOffice call per image, or batched? (`--convert-to` accepts several input files; this was not measured.)
- **Q4 (§14.5/§14.7):** how should a `draw:image` with an external `xlink:href` and no `office:binary-data` be handled: an unsupported finding (which feature id?), or dropped?
- **Q5 (§14.3):** `BlockUntrustedRefererLinks` could not be shown to have any effect, because no fetch happened even without it. Can we rely on that, given the setting is seeded anyway? Or is a different test case needed, such as a linked image in a section or OLE?
- **Q6 (CL-16, V2):** ODF → xlsx recalculated a stale cached value (99 → 2), even with `ODFRecalcMode=1` seeded and a LibreOffice generator string. Export of sheets through LibreOffice may therefore not preserve the cached values. This needs a V2 decision or a further spike (other config paths, or setting the values on export).
- **Q7 (§14.4):** `maxFlatXmlBytes = 4 × maxFileBytes`. Observed flat-to-package ratios were 6.3× (small file, style overhead) and about 40× (a reused image). Is 4× of the configured maximum still the intended cap?
- **Q8 (not done):** the Linux results (§9) are still owed. Who runs them, and on which LibreOffice version?
