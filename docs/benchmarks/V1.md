# V1 benchmark (task V1-41, spike S4)

Numbers for connections per Core, op latency, fan-out, LibreOffice export and import time, and typing work at 300 pages. Raw JSON is in `bench/results/full/`. Rerun with `npm run build && npm run bench` (`--quick` is a smoke run whose numbers mean nothing; also `--only=<stage>`, `--mode=main|worker`, `--limit-min=<n>`).

## Environment

| Item | Value |
|---|---|
| CPU | AMD Ryzen 9 9955HX, 16 cores / 32 logical |
| RAM | 31.3 GiB |
| OS | Windows 11 Home (10.0.26300) x64 |
| Node | v24.18.0 |
| LibreOffice | 26.8.3.1 |
| Chromium (Playwright) | 159.0.8154.6 |

One laptop-class Windows machine, nothing else heavy running while measuring. The engine runs in its own process (real Gateway, Core, queue, journal and storage; fake text codec). Clients run in separate load-generator processes. Both engine modes were measured: `main` (Core in the main process) and `worker` (Core in a worker thread).

## Method

- **Latency (item 2).** One document with 1, 10, 50, 100 clients (all but one type at 2 ops/s) and many documents (10, 100, 500 documents, two clients each, one typing). Ack = submit to acknowledgement at the typist; remote = submit to arrival at another client. 5 s warm-up, 20 s measured per row. CPU is from `process.cpuUsage` of the engine process (and of the Core worker).
- **Capacity (item 1).** Ramp of connected clients (5 per document; 2 ops/s per typist in the `typing` variant, none in `idle`), 10 s measured per step, stopping when p99 ack passes 100 ms, the generator saturates (its event-loop p99 over 75 ms), or clients fail to load. Generator event-loop p99 stayed at 20 to 26 ms, so the generators were not the limit.
- **Fan-out (item 3).** One typist at 20 ops/s on one document with N extra sessions; CPU per op = engine CPU over the window minus the idle baseline, divided by ops.
- **LibreOffice (item 4).** Real `CodecService` over the real codec pool. Documents are generated (about 6 paragraphs of 600 characters per page, a heading per ten) and calibrated so that LibreOffice's own PDF export has the requested page count within 3% (helper `modelForPages`, with a test). Timing: export (model to docx) and import (docx to model), 3 repeats sequentially, then 4 jobs submitted at once, at `libreoffice.maxConcurrent` 1 and 2. Includes the LibreOffice process start, as in production.
- **Typing (item 5).** Real Chromium, the real editor with the sync plugin, a 300-page document (1800 paragraphs, page count read from the editor's own pagination), 400 keystrokes after a 60-key warm-up at each of the start, middle and end of the document, one key per frame. `total` = transaction (`sync`) + pagination pass + forced layout.

### LibreOffice export and import, and flat-XML size (S-15)

| Pages | docx | flat XML written by export | flat XML read by import (LibreOffice docx to fodt) | import flat XML / docx | import flat XML as % of cap |
|---|---|---|---|---|---|
| 10 | 7.2 KiB | 51 KiB | 87 KiB | 12.1x | 0.003% |
| 100 | 17.7 KiB | 458 KiB | 504 KiB | 28.4x | 0.015% |
| 300 | 40.9 KiB | 1.33 MiB | 1.40 MiB | 35.0x | 0.044% |

The cap is `maxFlatXmlBytes` = 64 x `maxFileBytes` = 3200 MiB (3 355 443 200 bytes). The flat-XML to docx ratio grows with size and is 35x at 300 pages of plain text, so the cap is far from being hit by text documents of this kind. The ratio is for text that compresses extremely well (repeated sentences, no images, no styles); real documents with images or many styles compress less and would show a lower ratio, but this benchmark did not measure them. The docx files here are far below `maxFileBytes` (50 MiB). A cap of 4x (the old value) would already be exceeded at 100 pages (28x), which supports S-15.

Time (median of 3, ms, sequential, `maxConcurrent` 1 / 2):

| Pages | export | import | 4 exports at once, wall | 4 imports at once, wall |
|---|---|---|---|---|
| 10 | 1662 / 1675 | 2459 / 2459 | 6643 / 3975 | 9823 / 5939 |
| 100 | 2103 / 2273 | 2986 / 3025 | 8427 / 4997 | 12146 / 6895 |
| 300 | 2981 / 3037 | 4055 / 4062 | 12029 / 7445 | 16267 / 9447 |

Process start dominates small documents (about 1.5 s); a 300-page document costs about 3 s to export and 4 s to import. With concurrency 1 four simultaneous jobs take about four times a single job; with 2 they take about 2.5 times, a 40% cut in wall time. Run-to-run variation is large on this machine: an earlier saved run of the same stage showed about 1.0 s for a 10-page export against 1.66 s here.

### Capacity (connected clients per engine process)

| Mode and variant | Last step with no failure | First step that stopped the ramp | RSS at last good step |
|---|---|---|---|
| main, idle | 6000 | 8000: 376 clients failed to load | 238 MiB |
| main, typing (2 ops/s per typist, 1 in 5 clients) | 500 (p99 ack 68 ms) | 1000: p99 ack 108.8 ms, 67 failed to load | 104 MiB |
| worker, idle | 500 | 1000: 128 failed to load | 68 + 68 MiB |
| worker, typing | 1000 (p99 ack 60 ms, p95 19.8 ms) | 2000: p99 ack 112.8 ms | 123 + 191 MiB |

**The failures to load were a harness limit, not an engine limit (diagnosed in the V1-41 follow-up).** Every failed client in the reproductions failed the same way: `ECONNREFUSED` at TCP connect, 0 to 47 ms after `connect()`, before any HTTP upgrade. The harness started 8 generators x 50 connects at once (400 simultaneous), and the engine process's accept queue holds about 234 connections on this machine (Windows 11) whatever backlog `server.listen` is given (511, 4096 and 2147483647 gave the same failures); when the process's event loop is busy, the excess is refused by the OS. A bare `net` server with no open_docex code, blocking 5 to 20 ms per accepted socket, connected 234 to 240 of 400 simultaneous connects and refused the rest (`bench/accept-probe.mjs`). With the connects bounded to 128 in flight over all generators (`MAX_CONNECTS_IN_FLIGHT` in `bench/net.mjs`) the same steps loaded every client: worker idle 1000 clients 0 failed (2 runs; with the old 400 in flight, same code: 494 failed), main idle 2000 clients 0 failed (old: 1005), latency 500 documents (1000 clients) 0 failed in main and worker (old: 580 and 655). The engine's own warn/error logs, `error` events and faulted-document events were empty in all runs, the slowest load was 0.2 to 0.8 s (hello timeout is 30 s), and no WebSocket close code or HTTP status other than the refused connect was seen. The idle numbers above are therefore lower bounds set by the old harness, not engine limits; the table is NOT re-measured. A partial re-run of the main-mode idle capacity ramp with the fix (`node bench/stage.mjs capacity main`, full parameters, one run) loaded 250, 500, 1000, 2000, 3000, 4000, 6000 and 8000 clients with 0 failed to load (the machine was suspended for about 40 minutes between the 6000 and 8000 steps, so that run's timings and its 8000 window are not valid, and it was stopped before the typing variant). Main-mode typing, worker mode, and the full latency step were not re-run with the fix. A real deployment on Windows that receives more than about 230 new connections in one burst will see the same refusals; that is an operating-system limit of the listening socket, and the listening server is the adopter's (`http.server` option), not the engine's. Linux was not tested.

### Fan-out (one typist at 20 ops/s, N extra sessions on the document)

| Sessions | main CPU per op | main ack p95 / p99 | worker: main-thread CPU per op | worker: Core CPU per op | worker ack p95 / p99 |
|---|---|---|---|---|---|
| 12 | 0.86 ms | 1.41 / 4.95 | 0.83 ms | n/a | 3.00 / 6.44 |
| 102 | 3.5 ms | 1.61 / 2.61 | 2.9 ms | 0.3 ms | 2.65 / 5.57 |
| 502 | 12.9 ms | 1.58 / 5.44 | 10.8 ms | 0.7 ms | 2.65 / 6.51 |
| 1002 | 24.2 ms | 1.69 / 6.11 | 20.0 ms | 0.6 ms | 2.95 / 6.53 |
| 2002 | 43.2 ms | 46.4 / 59.2 | 33.2 ms | 0.3 ms | 16.5 / 47.1 |

CPU per op grows linearly with the session count (about 20 to 24 us per session per op: frame forwarding and socket writes). At 20 ops/s, 1000 sessions cost about 48% of a core in main mode and 40% on the main thread in worker mode; at 2000 sessions main mode reaches 86% and latency collapses. The Core itself uses under 1 ms per op in worker mode: the fan-out cost is in the Gateway, which stays on the main thread in both modes. The first row (2 sessions) of the main run has a 215 ms p99 and a negative CPU figure: a warm-up and baseline artefact, ignore it.

## Caveats

- One Windows machine (high-end laptop CPU), a single run of each stage, noisy. p99 and max values moved by tens of ms between rows for no visible reason.
- Network stages use the fake text codec: no real LibreOffice work ran in the capacity, latency or fan-out stages. They use plain localhost WebSockets, so no TLS, proxy or real network latency.
- The saved capacity, latency, fan-out and typing results come from the previous worker's full run. They were checked for sanity here (non-empty, ordered percentiles, plausible) but not re-run, and they have no `complete` flag (an earlier file format). Only the LibreOffice stage was re-run, with the corrected document generator.
- Generated documents are plain repeated prose. No images, tables, styles or sheets were measured; sheet operations were not benchmarked.
- The load failures in the capacity and latency stages came from the harness connecting 400 clients at once into a listen queue of about 234 (see Capacity); the saved numbers above were measured before that was fixed, so their failed-to-load counts and the stop points of the idle ramps are harness artefacts. A short run (1.5 s warm-up, 3 s measured, not the full parameters) of the 500-document latency step with all 1000 clients loaded gave ack p99 167 ms in main mode and 151 ms in worker mode, against 60.8 and 77.7 ms in the table above, which measured only the 420 and 345 clients that had loaded: treat that row as understated until it is re-run with the full parameters.

## PROPOSAL: new default limits

This is a proposal for the project owner. A change to the defaults is an HLD/LLD change; nothing here is applied.

The current defaults (`backend/src/api/validate-options.ts`) are `queue.perDocument` 1000, `queue.global` 50 000, `libreoffice.maxConcurrent` 2, `libreoffice.timeoutMs` 120 000, `maxFileBytes` 50 MiB, `maxFlatXmlBytes` 64x, `ws.maxPayloadBytes` 16 MiB.

1. **Keep** `maxFlatXmlBytes` at 64x `maxFileBytes`. The measured need (35x for very compressible text) is below it; if a lower value is wanted, do not go under 40x.
2. **Keep** `libreoffice.maxConcurrent` at 2: it cut the wall time of four simultaneous jobs by about 40% against 1. Higher values were not measured. `timeoutMs` 120 000 is about 30 times the measured 300-page import (4 s). Real documents with images were not measured, so there is no evidence to lower it.
3. **Document a recommendation, not a hard limit,** of about 500 active clients per engine process in main mode and about 1000 in worker mode (p99 ack under 100 ms at 2 ops/s per typist), and no more than about 100 clients per document unless fan-out cost is acceptable (one document with 1000 sessions costs about half a core at 20 ops/s). New options such as `limits.maxClientsPerDocument` (suggest 500) and `limits.maxConnections` (suggest 2000 in worker mode) would be an API addition for the owner to decide.
4. **Keep** `queue.perDocument` 1000 and `queue.global` 50 000: at the measured rates (up to 100 ops/s per document) 1000 queued ops is 10 s of backlog, and no evidence was gathered for changing them.
5. **Re-measure** on the target deployment hardware and on Linux (capacity and the 500-document latency step with the fixed harness) before relying on any of these.
